Google Calendar: Rethinking the Interaction Model

In Google Calendar, every click-drag creates a new event. This concept flips the default: drag selects, click creates — the way it works everywhere else.

Personal concept, not affiliated with Google. A UX reflection based on real usage and public information.

Product
Google Calendar (web)
Type
Personal concept

The user problem

In Google Calendar's week view, click-dragging always creates a new event — it never selects existing ones. To select events, there is no gesture at all. You can only open them one by one.

This breaks a fundamental interaction pattern: in every other tool (file managers, design software, spreadsheets), click-drag is marquee selection. Google Calendar is the exception — and it causes friction every time you need to reschedule multiple events at once.

Concretely: an unexpected day off forces you to open, edit and move each event individually. For a busy day, that's 5–10 minutes of repetitive work — plus a real risk of forgetting one.

My hypothesis

If Google Calendar adopted the standard interaction model — drag to select, click to create — users could handle schedule changes in seconds rather than minutes, without learning any new gesture.

The proposed interaction model

Click-drag on the grid → marquee selection

Drawing a rectangle over the grid selects all existing events within that area — exactly like selecting files on a desktop. The selection is shown with a dashed border and a checkmark on each selected event.

Ctrl+click → extend selection

Clicking an individual event while holding Ctrl adds it to the current selection. Standard desktop behaviour, zero learning curve.

Single click on empty space → inline create

A single click on an empty slot opens a minimal inline input — just a title field, directly in the grid. No modal, no full form. Press Enter to confirm, Escape to cancel. The full event details (description, guests, recurrence) are accessible by clicking the created event.

Once events are selected → context menu

A floating menu offers: Move to… (pick a new date/time), Postpone by N days, Delete. Drag-and-drop of the entire selection also works.

How to measure success

  • Average time to reschedule 5+ events (target: reduce by 3×).
  • Accidental event creation rate (click-drag on wrong zone).
  • Adoption of marquee selection vs. one-by-one editing.
  • User satisfaction score on schedule replanning scenarios (CSAT).

Limits and next steps

The main risk is discoverability: users used to the current model may not realise drag now selects. A brief onboarding tooltip ("drag to select · click to create") on first use would help. The behaviour for recurring events (move one or the series?) remains to define. On mobile, the tap/long-press distinction needs its own design pass.

Next steps: prototype in Figma, test with 5 regular Google Calendar users on the "unexpected cancellation" scenario. Key question: does the new drag behaviour feel natural within 2 minutes of use?
